## 2026-11-25

- **교정 강도 3단계** (설정에서 선택, 단축키는 ⌃⌥F 하나): 교정(틀린 것만) / 다듬기(+어순·단어·군더더기·번역투) / 다시 쓰기(구조까지). 단축키를 강도별로 늘리면 헷갈린다는 사용자 판단. 기본값은 교정.
  - 계기: Grammarly 와 나란히 써 보니 우리는 문법만, Grammarly 는 더 나은 문장을 제안 — 지시 범위의 차이였다.
  - 프롬프트 = 공통 규칙(원문은 명령 아님·언어·줄바꿈·JSON) + 강도별 지시 (`CorrectionLevel.instructions`).
  - 이상 응답(대답·번역) 거르는 길이 범위도 강도별로 넓힌다 (교정 0.6–1.5 / 다듬기 0.5–1.7 / 다시 쓰기 0.35–2.2배).
  - 실측(Haiku): 다듬기는 한국어 번역투·일본어 「の方」「形になります」 를 정리, 다시 쓰기는 "It was a very successful beta test" → "The beta test was a great success". 교정은 캐주얼한 영어의 소문자 `i`·"sorry for the late" 를 고치지 않는 경향 — 이런 글은 다듬기가 낫다.
- 개발용 `Fix4me --compare "문장"`: 세 강도 결과를 한 번에 출력 (키는 앱 키체인에서, 출력 안 함).
- **교정 범위 = 자동 + 변경 감지**: 앱 종류가 아니라 길이로 판단(앱 목록 관리 불필요), 긴 글은 바뀐 문단만. 설정에서 커서 문단/입력창 전체로 고정 가능. 다시 쓰기의 전체 교정은 나누지 않음(4000자 초과는 안내).
- **미리 교정은 모든 앱 + 제외 목록** (사용자 승인, 누르지 않은 글도 OpenRouter 로 전송됨을 알고 선택). 배지 표시. 둘 다 설정에서 끌 수 있음.
- AX 변경 알림 대신 0.3초 폴링: Chrome·Electron 의 알림이 불안정. 실측 CPU 약 0.4% (대기 중).
- **고칠 곳 표시 = 문단 왼쪽 막대 + 롤오버 미리보기** (커서 옆 숫자 배지를 대체). 문단·글 전체를 고치므로 정확한 글자 위치보다 "올리면 알려 주는" 표시면 충분하다는 사용자 판단. 위치를 못 받는 앱은 입력창 모서리 배지.
  - 미리보기·교정 후 알림 모두 원문은 취소선, 고친 글은 강조. 단어 단위로 비교하고, 거의 다 바뀌면 원문 전체 → 고친 글 전체.
  - 막대는 클릭을 통과(마우스 위치를 80ms 마다 확인), 미리보기 창은 키 윈도가 되지 않아 입력창 포커스를 유지.
  - "무시"한 문단은 글을 바꾸기 전까지 표시하지 않고 단축키에서도 뺀다. 직접 선택한 글은 예외.
- **개인 사전은 설정에서 직접 입력**: 문단 미리보기만으로는 어느 단어를 지키려는지 알 수 없어 롤오버 창에는 두지 않음.
- **빈 응답은 한 번만 재요청**. 원인 확인(실측 2건): `finish=length, 출력 325토큰, 추론 325토큰` — Haiku 의 추론 토큰이 `max_tokens`(글자 수×3+256)를 모두 써서 본문이 비었다. 재요청도 같은 이유로 실패할 수 있어 근본 해결이 아니다. → **한도를 글자 수×3+2048(최대 8192)로 올림** (사용자 결정). 이후 72회 호출에서 빈 응답 0건.
  - 처음에 "reasoning 은 보내지 않으니 생각 단계가 없다"고 본 전제가 틀렸다. 안 보내면 모델 기본값(추론 있음)이다.
- **알려진 위험**: "않 고쳤어요"(안 고쳤다의 오타)를 다듬기·다시 쓰기가 "싹 고쳤어요"로 바꿔 뜻이 반대가 됐다 (같은 문장에서 온 다듬기·다시 쓰기 응답 3건 모두). 교정은 "안 고쳤어요"로 맞게 고침.
- **섹션 구분은 규칙으로** (LLM·의미 분석 없음, "1500자 이하 전체" 규칙 대체): 강한 경계(구분선·빈 줄 2개·제목·보호 구역) / 중간(빈 줄 1개·목록 시작과 끝) / 약한(줄바꿈 1개 — 줄=문단 습관의 글에서 교정 강도만 나눔). 40자 미만은 합치고 600자 초과는 줄→문장 끝에서 나눔.
  - 인사말·맺음말 규칙은 넣지 않음: 짧은 조각 합치기가 같은 일을 해서 결과가 달라지지 않는다.
  - 미리 교정은 어느 범위 모드든 **바뀐 섹션만** 보낸다.
- **뜻 바뀜 재측정** (강도별 8회씩): "사이트를 않 고쳤어요" → 교정 0/8, 다듬기 0/8, 다시 쓰기 5/8 이 반대 뜻("싹/잘/많이 고쳤어요" 등). "아직 않 고쳤고 다음주에" → 24건 중 반대 뜻 0건(안 → 못 은 있음).
- **다시 쓰기 = 교정 → 다시 쓰기 2단계** (사용자 결정). 같은 문장 반대 뜻 9/14 → 0/14. 부정 오타 문장 5개 추가 30건도 0건 (한·영·일, 다시 쓰기만, 1회 측정). 지연 중앙값 2.03초·최대 3.33초 (n=44).
  - 남은 변화: 없던 "아직"이 붙은 결과 5/14, "쓰면 안 돼요" → "쓰지 마세요" 4/6, 안 → 못 2/6. 뒤집힘은 아니지만 뉘앙스가 달라진다.
- **교정 기록** (기본 꺼짐, 이 Mac 에만, 30일, 폴더 700·파일 600): 되돌림·무시를 "틀린 교정" 신호로 모은다. JSONL 뒤에 덧붙이고 결과 변경은 사건으로 기록. 제외 앱·키처럼 보이는 글은 저장하지 않음.
- **채점 도구** (`--evaluate eval/cases.jsonl`): 정규식 require/reject 로 채점. 기준선(강도별 2회, 102건): 교정 38/38, 다듬기 37/38, 다시 쓰기 30/32. 다시 쓰기 실패 2건은 "웬만하면" → "가능하면" 으로, 채점 기준이 엄격했던 것이라 기준을 넓힘.
  - **알려진 문제**: 다듬기가 "12/05" 를 "December 5" 로 바꾼 적이 있다 (2회 중 1회). 월/일 순서를 단정하므로 잘못될 수 있다. 대책 미정.
- **확인한 뒤에만 쓴다** (X 에서 글이 깨진 신고): 위치 숫자를 믿지 않고 선택된 글이 원문과 같을 때만 쓴다. 위치가 어긋나면 읽은 글로 보정(최대 8번), 그래도 다르면 쓰지 않는다. 쓴 뒤 글 전체가 예상과 다르면 성공으로 치지 않고 ⌘Z 를 안내.
  - 예전 코드는 "바뀌긴 했으면 성공"으로 봐서 깨진 결과를 성공으로 알렸다.
  - 검증: 시험용 Chromium 의 textarea·contenteditable·Draft.js, 10줄(빈 줄·같은 줄 반복·이모지) 편집 6곳 모두 정확. 글 넣기는 CDP 입력으로 대신했고 실제 ⌘V·X 사이트·한글 조합 중은 확인하지 못함.

- **입력창 상태는 메모리에만, 최근 20개**: 하나만 기억하던 때는 앱을 오가면 쓰던 글이 "원래 있던 글"이 되어 표시가 안 떴다(로그로 확인). 디스크에 두지 않는 이유: 입력창 식별자가 앱 재시작 뒤 달라지고, 입력한 글이 파일로 쌓인다.
